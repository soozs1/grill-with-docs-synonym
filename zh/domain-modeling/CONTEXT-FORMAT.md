# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一到两句话：这是什么上下文，以及它为何存在。}

## 语言

**Order / 订单**：{一到两句话：它是什么}
_Avoid_: Purchase, transaction, 购买

**Invoice / 发票**：交付完成后发给客户的付款请求。
_Avoid_: Bill, payment request

**Customer / 客户**：下达订单的自然人或法人。
_Avoid_: Client, buyer, account, 买家
```

## 规则

- **区分完全同义词与部分同义词。** 完全同义词（在任何场景下都可互换：review / 评审）用带空格的 `/` 并列为规范。部分同义词（在某个场景中分歧：客户 / 买家）—— 一个进规范，其余进 `_Avoid_`。
- **与代码相关的概念 —— 英文在前。** 如果术语映射到代码（类、函数、表、文件），规范中的第一个选项就是英文/拉丁文：`Order / 订单`。这是信号，而非约束；并没有显式的“代码形式”字段。
- **态度要决断。** 敲定规范 —— 一个术语，或以 `/` 连接的一组完全同义词 —— 其余一律放入 `_Avoid_`。
- **定义要简短。** 最多一到两句话。定义它**是**什么，而非它**做**什么。定义用团队的工作语言书写。
- **只收录对本项目上下文而言特定的术语。** 通用的编程概念（超时、错误类型、工具类模式）不属于这里，即便项目大量使用它们也是如此。在添加术语之前，先问一句：这个概念是本上下文所独有的，还是一个通用编程概念？只有前者才属于术语表。
- **当自然聚浮现时，把术语归到小标题之下**。如果所有术语都属于同一个连贯的领域，那么平铺列表也无妨。

## 单上下文与多上下文仓库

**单个上下文（大多数仓库）：** 仓库根目录一个 `CONTEXT.md`。

**多个上下文：** 根目录的 `CONTEXT-MAP.md` 列出各上下文、它们的位置以及彼此如何关联：

```md
# 上下文地图

## 各上下文

- [Ordering](./src/ordering/CONTEXT.md) —— 接收并跟踪客户订单
- [Billing](./src/billing/CONTEXT.md) —— 开具发票并处理付款
- [Fulfillment](./src/fulfillment/CONTEXT.md) —— 管理仓库的拣配与发货

## 关联

- **Ordering → Fulfillment**：Ordering 发布 `OrderPlaced` 事件；Fulfillment 消费它们以开始拣配
- **Fulfillment → Billing**：Fulfillment 发布 `ShipmentDispatched` 事件；Billing 消费它们以开具发票
- **Ordering ↔ Billing**：`CustomerId` 与 `Money` 的共享类型
```

技能自行判断适用哪种结构：

- 如果存在 `CONTEXT-MAP.md` —— 读取它以找到各上下文
- 如果只有根目录的 `CONTEXT.md` —— 即为单个上下文
- 如果两者都没有 —— 则在敲定第一个术语时，惰性创建根目录的 `CONTEXT.md`

当存在多个上下文时，判断当前话题属于哪一个。如果不清楚 —— 就问。
