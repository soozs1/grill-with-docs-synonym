# ADR 格式

ADR 存放在 `docs/adr/` 中，采用连续编号：`0001-slug.md`、`0002-slug.md` 等。惰性创建 `docs/adr/` 目录 —— 只在需要第一个 ADR 时才建。

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么，决定了什么，以及为什么。}
```

就这些。ADR 可以只有一段。价值在于记录*已经做出了什么*决策以及*为什么* —— 而不在于填满各个章节。

## 可选章节

只有在它们确实增添价值时才纳入。大多数 ADR 用不上。

- frontmatter 中的**状态**（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 当决策会被重新审视时有用
- **考虑过的备选方案** —— 仅当被舍弃的替代方案值得记住时
- **后果** —— 仅当需要点明不明显的下游效应时

## 编号

扫描 `docs/adr/` 找出现有的最大编号，再加一。

## 何时提议 ADR

必须三条全部成立：

1. **难以逆转** —— 日后反悔的代价切实可感
2. **离开上下文就不明显** —— 未来的读者会看着代码问“他们为什么这样做？”
3. **真实权衡的结果** —— 曾有真正的备选方案，而你们基于具体理由选择了其一

如果决策容易逆转 —— 就跳过，你大可以日后直接推翻它。如果它不令人意外 —— 没人会去问“为什么”。如果根本没有真正的替代方案 —— 除了“我们做了显而易见的事”，没什么可记录的。

### 什么适合写 ADR

- **架构形态。** “我们使用 monorepo。”“写模型采用 event-sourcing，读模型投影进 Postgres。”
- **上下文之间的集成模式。** “Ordering 与 Billing 通过领域事件通信，而非同步 HTTP。”
- **带有 lock-in 的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都值得 —— 只有那些换掉要花一整个季度的才算。
- **关于边界与职责范围的决策。** “Customer 的数据归 Customer 上下文所有；其他上下文只能通过 ID 引用它们。”明确的“不”与“是”同样有价值。
- **对显而易见路径的刻意偏离。** “我们使用纯 SQL 而非 ORM，因为 X。”凡是合理读者会做出相反假设的地方都算。这能防止下一位工程师去“修复”一处刻意为之的设计。
- **代码中看不见的约束。** “由于合规要求，我们不能使用 AWS。”“由于与合作伙伴 API 的契约，响应时间必须小于 200 毫秒。”
- **当舍弃并不显而易见时，记录被舍弃的备选方案。** 如果你们曾考虑 GraphQL，并出于微妙理由选择了 REST —— 就写下来，否则半年后又会有人提议 GraphQL。
