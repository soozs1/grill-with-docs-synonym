# Доменное моделирование

Активно строй и оттачивай доменную модель проекта по ходу проектирования. Это *активная* дисциплина: оспаривать термины, придумывать граничные кейсы и записывать глоссарий и решения в тот самый момент, когда они кристаллизуются. (Просто *читать* `CONTEXT.md` ради словаря — это не этот скилл; это однострочная привычка, доступная любому скиллу. Этот скилл — для случаев, когда ты меняешь модель, а не просто пользуешься ей.)

## Структура файлов

Большинство репозиториев имеют один контекст:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

Если в корне есть `CONTEXT-MAP.md`, в репозитории несколько контекстов. Карта указывает, где лежит каждый из них:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                       ← общесистемные решения
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/              ← решения конкретного контекста
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

Создавай файлы лениво — только когда есть что записать. Если `CONTEXT.md` ещё нет, создай его, когда будет зафиксирован первый термин. Если нет `docs/adr/`, создай её, когда понадобится первый ADR.

## Язык

Веди сессию на рабочем языке пользователя (по умолчанию — на русском).

В глоссарии разделяй *канонический термин* и его *определение*.

- **Канон зеркалит код.** Канонический термин записывай так, как он живёт в проекте. В свежем проекте (greenfield) — один раз спроси команду, сразу предложив билингвальные варианты («назовём *Order / Заказ*?»), и зафиксируй выбор.
- **Полные синонимы — со-канонически, через `/`.** Если термины тождественны по смыслу и взаимозаменяемы в любом сценарии (ревью / review, парсинг / parsing), пиши их в каноне через `/` с пробелами: `Order / Заказ`. Их может быть больше двух.
- **Частичные синонимы — в `_Avoid_`.** Если термины похожи, но в каком-то сценарии расходятся по смыслу (аккаунт / пользователь / клиент), выбери один канон, остальные вынеси в `_Avoid_`.
- **Порядок = мягкий сигнал для кода.** Для концептов, связанных с кодом (мапятся в класс, функцию, таблицу, модуль, файл), первым в каноне идёт английский/латинский термин: `Order / Заказ`. Явного поля «форма для кода» нет, и это не ограничение: агент ориентируется на английскую форму для идентификаторов, но выбор средств именования свободен. Чисто разговорные концепты могут идти русским первым.
- **Определение** — на рабочем языке, одно-два предложения, «что это есть». `_Avoid_` — список через запятую (порядок не важен), включает и английские, и русские отвергнутые формы.

Цель — чтобы термины в глоссарии совпадали с тем, как они называются в коде и в речи команды. Утверждённые термины агент переиспользует; слой персистентности — `CONTEXT.md`. Если команда предпочитает иную конвенцию (полностью русскоязычный глоссарий, транслит в идентификаторах) — ок, будь последователен и зафиксируй выбор в ADR.

## По ходу сессии

### Сверяйся с глоссарием

Когда пользователь употребляет термин вразрез с существующим языком в `CONTEXT.md`, сразу обращай на это внимание: «В глоссарии "отмена" определена как X, но ты, похоже, имеешь в виду Y — так что из этого?»

### Оттачивай размытые формулировки

Когда пользователь использует расплывчатые или перегруженные термины, предлагай точный канонический термин: «Ты говоришь "аккаунт" — ты имеешь в виду Customer или User? Это разные вещи.»

### Устанавливай полные синонимы

Когда у термина есть кандидаты в синонимы, предложи их пользователю: утвердить, отвергнуть или отложить («назовём *погрилить / grilling*, или обсудим позже?»). «Отложить» — это escape-hatch в диалоге; в запись глоссария попадают только утверждённые синонимы.

Эвристика — **тест подстановки**: термины — полные синонимы, только если их можно поменять местами в любом предложении и сценарии без сдвига смысла. Если можешь построить сценарий, где они расходятся, — **обязан один раз явно предъявить его** («вот сценарий, где X и Y — разные вещи; точно сливаем?»). Это предупреждение о риске, а не вето: решение за пользователем. Утвердил, увидев контрпример, — пишем полный синоним через `/`. Отверг — один канон, остальное в `_Avoid_`. Предупреждение однократное, без пиления. Утверждённые термины далее переиспользуй и фиксируй в `CONTEXT.md` на месте.

### Обсуждай конкретные сценарии

Когда обсуждаются связи между доменными понятиями, проверяй их на конкретных сценариях. Придумывай сценарии, которые щупают граничные кейсы и заставляют пользователя чётко обозначить границы между концептами.

### Сверяйся с кодом

Когда пользователь утверждает, как что-то работает, проверяй, согласуется ли это с кодом. Если находишь противоречие — вскрывай его: «Код отменяет заказы целиком, но ты только что сказал, что возможна частичная отмена — что из этого верно?»

### Обновляй CONTEXT.md на месте

Когда термин зафиксирован, сразу обновляй `CONTEXT.md`. Не копи их пачкой — фиксируй по мере появления. Используй формат из [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md). `CONTEXT.md` должен быть полностью свободен от деталей реализации. Не превращай `CONTEXT.md` ни в спецификацию, ни в черновик, ни в хранилище реализационных решений. Это глоссарий и ничего больше.

### Предлагай ADR экономно

Предлагай создать ADR, только когда верно всё из трёх:

1. **Трудно обратить** — цена передумать позже ощутима
2. **Неочевидно без контекста** — будущий читатель спросит «почему они сделали это так?»
3. **Результат реального компромисса** — были настоящие альтернативы, и вы выбрали одну по конкретным причинам

Если хотя бы одного из трёх нет — пропускай ADR. Используй формат из [ADR-FORMAT.md](./ADR-FORMAT.md).
